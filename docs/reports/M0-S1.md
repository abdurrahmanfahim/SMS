**Status:** Partial

## Understanding
I built three synthetic A4 marksheet layouts under `spikes/pdf/`, then compared three ways to turn them into a PDF a guardian or teacher can view/share/print from a phone: (A) print CSS exported to PDF via a browser engine, (B) that same engine run server-side (Playwright/Chromium) with timing and cost numbers, (C) a client-side PDF library with an embedded Bangla font. I did not touch production code or pick a final marksheet design. Proof is saved PDFs/screenshots under `docs/research/pdf-spike/`, a Bangla shaping stress test, and real timing/memory output. Two things could not be proven here and are left unticked rather than claimed: real headless-Chromium numbers (this container cannot reach Playwright's browser download, and Ubuntu 24 has no installable non-snap Chromium), and any on-device phone test (no physical Android/iPhone reachable from this environment).

## Summary
Print-CSS through a real browser engine is the right direction for D-12. Tested with wkhtmltopdf (a WebKit engine already present, substituting for the specified Chromium, which this container cannot reach) it renders all three layouts correctly, handles Bangla conjuncts and Bangla-digit rendering correctly, and even does automatic script-fallback for a stray Arabic-script name — something the tested client-side library (pdfkit) could not do (it rendered Arabic as tofu boxes). The 100-student batch paginates correctly in 7.7s but produces a 32.5 MB file (317 KB/page), which looks like a font-deduplication problem worth re-checking with real Chromium. Full details, screenshots, and the recommendation are in `docs/research/pdf-spike.md`.

## Deviations and assumptions
1. **Approach A/B tested with wkhtmltopdf, not Chromium.** Playwright could not download a Chromium binary (network allowlist blocks its CDN) and Ubuntu 24's own `chromium-browser` package is a snap-only transitional shim (no snapd in this container). wkhtmltopdf (Qt WebKit) was already installed and used as the closest available substitute so the spike could produce real rendering/timing evidence instead of none. Every number sourced this way is labelled in the research doc; it is not presented as a Chromium result.
2. **Real student-name samples not available** (M0-O1 not yet delivered to this task) — used the synthetic Bangla stress-test set the task file specifies as the starting point instead.
3. **Phone evaluation (step 5) not performed** — no physical or emulated Android/iPhone device is reachable from this sandboxed environment. Listed as a gap rather than skipped silently.

## Known issues and debt
- The wkhtmltopdf-rendered 100-student batch is 317 KB/page (32.5 MB for 100 students) — looks like the embedded font isn't being shared across pages. Needs re-verification with real Chromium before any batch-PDF feature is built on this pattern.
- `approach-c/render.mjs` (pdfkit) has no per-script font fallback; any name mixing in a non-Bengali, non-Latin script will render as tofu boxes. Not a bug to fix here — it's the finding that rules Approach C out for names with script mixing.

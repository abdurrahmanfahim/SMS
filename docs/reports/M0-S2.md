## Deviations and assumptions

- **The restart test reconnects just before reloading, rather than reloading while offline.** A literal page reload while the browser context is offline would fail to load the page at all (no service worker here caches the app shell — that's explicitly a separate concern from queueing writes, per D-06's "no full offline replica"). What actually needed proving — that a queued op survives in IndexedDB across a reload, rather than living only in memory that a reload would wipe — is still proven: the test checks the summary immediately after reload, before triggering any sync.
- **That same test surfaced a real bug, now fixed in `src/outbox.ts`:** reconnecting fires a genuine browser `online` event, which the harness uses to auto-trigger a sync; the reload can interrupt that sync mid-flight, leaving the op stuck in `"syncing"` forever (nothing was watching for it). Fixed by having `sync()` recover any stuck `"syncing"` op at the start of every call, immediately eligible again (no backoff, since the interruption says nothing about network health) — safe specifically because `apply_ops` is idempotent, so at worst recovery re-sends something already applied and gets `duplicate:true` back. Both the fix and two dedicated unit tests are in `src/outbox.ts`/`src/outbox.test.ts`; the e2e restart test now also exercises this path for real. Documented in full in `docs/research/offline-spike.md`.
- **`apply_ops` runs against an embedded Postgres inside the spike (`@electric-sql/pglite`), not `supabase/migrations/`.** `supabase/*` is outside this task's owned paths (`spikes/offline/**` only per §5.3), and this is explicitly a prototype — the real migration is M2-E2/M2-A5's job. `db/schema.sql` and `db/apply_ops.sql` are a validated starting point for that migration, stated as such in the research doc, not offered as the migration itself.
- **`pnpm db:reset && pnpm db:test` cannot run in this sandbox** — Docker is not installed here, a pre-existing limitation M0-P2's own report already documented in detail and which still holds (`docker: not found`, confirmed again — see Verify output). This is unrelated to this task, since nothing here touches `supabase/*`; included for completeness since §6 names this command.

## Decisions others depend on

- `apply_ops`'s request/response shapes, `reason` codes, and `duplicate` semantics (see `docs/research/offline-spike.md`) are the contract M2-E2/M2-A5 should implement against.
- Conflict policy is last-write-wins by **delivery order, not client clock** — client timestamps are never trusted for ordering. This is a real, visible trade-off (a later sync can silently overwrite an earlier one from a different device with no merge or notification) that M2-E2/M2-A5 and its UI should account for, not just its SQL.
- Marks get an append-only audit trail (`marks_audit`); attendance currently does not. Worth a decision before the real implementation, since attendance disputes seem at least as likely as marks disputes.
- A rejected op (locked/finalised) is terminal on the client — never auto-retried, only ever cleared by a human action (unlocking server-side, or the user editing and re-queueing). The real UI must give the user *some* path forward from an Error state, not just display it.
- `sync()`'s recovery of interrupted (`"syncing"`) ops is safe *because* `apply_ops` is idempotent by `op_id` — if a future change to `apply_ops` ever weakens that idempotency guarantee, this client-side recovery becomes unsafe too. The two are a matched pair, not independent design choices.

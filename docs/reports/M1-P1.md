## Deviations and assumptions

- **`has_role` is the READ check; `has_role_write` is new.** permissions.md section 3 says `has_role` also lets a platform owner with a session pass "read only unless the session has write_access". One function cannot tell reads from writes, so I kept `has_role(inst, roles[])` exactly as specified (read) and added `has_role_write(inst, roles[])` for insert, update and delete policies. Later tasks must use `has_role_write` in write policies, or an impersonating platform owner could write without `write_access`. Needs the Leader to add it to permissions.md section 3.
- **Impersonation table does not exist yet** (M1-P3). `private.impersonating(inst, need_write)` and every ACAD-dependent helper check for the table and columns first and return false until they exist, so they start working on their own (no follow-up migration needed). Tested with minimal stand-in tables.
- **`students.profile_id` is assumed** for `private.is_student_self` (guardians have `profile_id`, but domain-model section 4 lists none for students). WS-ACAD must add `students.profile_id` (nullable) or the helper stays false.
- **`institution_settings` has no `id` column** (its primary key is `institution_id`), as domain-model section 2 specifies; this is the one exception to "every tenant table has `id` plus `unique (institution_id, id)`".
- `audit_log.institution_id` has no foreign key on purpose, so the log outlives an institution and no cascade can touch it. `actor_role` is checked against the six roles plus `system`.
- Audit actor: no signed-in user is `system`; a platform owner inside a session is `platform_owner` with `meta.impersonating = true`; otherwise the caller's most senior active role in the institution. A signed-in user with no role in the institution is `system` with `meta.actor_role_unresolved = true`.
- Policy scope of step 3: only the tables created in this task. The matrix rows "memberships, profiles, invites: institution admin full" are not added here (M0-P3's "read your own rows" policies stay unchanged); I read them as belonging to the invite and member-management task (M1-P2). `institution_settings` read: admin, teacher, accountant; guardian and student read only the institution name through `institutions` (a reading of the matrix's "R (name)").
- Storage access (my reading of the matrix): `logos` read by all five roles, write admin; `photos` read admin, teacher, accountant, write admin; `imports` admin only; `exports` read admin and accountant, written only by server code. Limits: logos 1 MiB, photos 2 MiB, imports 10 MiB, exports 25 MiB, with file-type allow-lists. Guardians and students get photos through server-created signed URLs.
- The local Supabase config has a global 50 MiB storage limit; the per-bucket limits are lower, so they apply.

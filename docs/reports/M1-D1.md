## Understanding

- I will build the pure utility layer in `packages/domain`: integer-poisha money (add, subtract, sum, allocate, format, parse), Asia/Dhaka date helpers (working days, academic-year lookup, display-only Hijri), Bangladeshi phone normalisation to E.164, Bangla/ASCII digits and numeric input, name normalisation and search keys, UUID ids, and shared zod schemas.

## Deviations and assumptions

- **`isoDate`'s validity check restructured to avoid an unreachable branch.** A naive "compare `Date.UTC` round-trip on year, month, and day" check has a branch (day mismatches while year and month still match) that I verified by brute-force search is mathematically unreachable — any day overflow always changes the month too. I instead bound month to 1–12 and day to 1–31 first, then compare only the day after the `Date.UTC` round-trip. This is why 100% branch coverage was achievable at all for this function; a Leader who wants the original 3-way comparison for readability should know it cannot reach 100% branch coverage as written.
- **`academicYearContaining` treats both range endpoints as inclusive** (`startsOn <= date <= endsOn`). `docs/spec/domain-model.md` only says `ends_on > starts_on`; it doesn't say whether `ends_on` is the last real day or the day after. I assumed inclusive-inclusive as the more natural shape for an admin filling in "starts on / ends on" fields. Easy to flip if the intended shape is half-open.
- **Zod major version:** picked `zod@^4.6.5` (current latest) since no other package in the repo depends on zod yet and there was nothing to match. All schemas use the `.transform((value, ctx) => { ctx.addIssue(...); return z.NEVER; })` pattern, which I verified works correctly under 4.6.5 — but if a later task assumed zod v3's API surface, that assumption should be corrected to v4, not this one.
- **Sandbox limitations, corrected from what I expected going in:** unlike M0-P1's precedent, this sandbox's GitHub PAT *could* open a pull request via the API (PR #6, linked above) — I'd assumed otherwise going in and should not have assumed a prior task's limitation applied here without testing it. Two narrower, real limits I did hit while monitoring CI: the `GET .../commits/{ref}/check-runs` endpoint returns 403 ("Resource not accessible by personal access token") for this PAT (I used `GET .../actions/runs` and `GET .../pulls/{n}` instead, which both work), and the Actions log-download host (`results-receiver.actions.githubusercontent.com`) is not on this sandbox's network egress allowlist, so I could watch job/step status but never read actual log content (see Verify output / Requests for what that meant for the final commit's CI run). Deno and a real `esbuild` browser bundle were both available in-sandbox and were used for real, not simulated, verification (see Acceptance criteria). `pnpm e2e` itself I still could not run directly here (no real browser in this sandbox), but I could watch the real CI run its own E2E step remotely.
- **UUID validation is version/variant-agnostic** — `ids.ts`'s `uuid()` accepts any RFC 4122 shape (8-4-4-4-12 hex) without checking the version nibble, so it validates a v1, v4, or v7 UUID the same way. `gen_random_uuid()` produces v4 specifically; I chose leniency over strictness since nothing in the spec asks this function to reject other UUID versions.
- **`normalizeNumericInput`'s "Bangla decimal and thousand separators"** turned out, on checking `Intl.NumberFormat("bn-BD-u-nu-beng")`'s actual output, to be the same ASCII `.` and `,` punctuation as English — Bengali has no separate Unicode decimal/thousands-separator characters (unlike Arabic, which does). The function converts digit script and strips grouping commas; it does not invent separator handling that Bangla numerals don't actually have.

## Decisions others depend on

- `academicYearContaining<T extends { startsOn: IsoDate; endsOn: IsoDate }>` expects **camelCase** field names, not the database's `starts_on`/`ends_on` — callers map their row shape before calling it.
- `IsoDate`, `Poisha`, `Uuid`, and `BdMobileE164` are branded `string`/`number` types, not classes — `poisha(x).value`, `isoDate(x).value`, etc. are the only supported way to produce one; nothing enforces the brand at runtime beyond that entry point, so don't hand-cast a raw string/number as one of these types elsewhere.
- `workingDaysBetween` and `academicYearContaining`'s range checks are both **inclusive of both endpoints** (see Deviations above).
- `parseTaka` rejects a leading sign, commas, and Bangla digits by design — always run raw human input through `normalizeNumericInput` (or the `takaInputSchema` zod schema, which does both steps) first.
- `phoneE164Schema` is strict (only already-canonical `+8801XXXXXXXXX` passes); use `bdPhoneInputSchema` for anything a person typed.

- **Edge cases decided (written into TSDoc at the point of decision):**
  - `isoDate`: month must be 1–12 and day 1–31 before the calendar-existence check even runs (see Deviations); `2026-02-30`, a non-leap `2026-02-29`, and `2026-04-31` are all rejected as `invalid_calendar_date`, not `invalid_format`.

## 3. Project context (so you are never lost)
- Product: a Bangla-first school management system for schools, madrasas and coaching centres in Bangladesh, built so an institution can run everything on a phone. It is a separate paid product; Munshi is a different, free, single-user app.
- Stack: TypeScript (strict), React 19, Vite, Tailwind, shadcn/Radix, Supabase (Postgres, RLS, Edge Functions), pnpm monorepo, Netlify.
- Layout: `apps/web`, `packages/{domain,db,ui,config}`, `supabase/`, `e2e/`, `docs/`.
- Tenancy: one database; every tenant row has `institution_id`; isolation is enforced by Postgres RLS, never by app code.
- Roles: platform owner, institution admin, teacher, accountant, guardian, student.
- Phone-complete: every task must work on a 360 px phone with touch only (Android first, iPhone second).
- Numbers: money in integer poisha; marks in integer hundredths inside calculations; never floating point.
- Language: Bangla first, English second; all user-visible text goes through i18n keys.
- Quality bar: WCAG 2.2 AA, `docs/spec/ux-standard.md`, and the Definition of Done in README section 9.

**Decisions in force for this task (do not reopen them):**
- D-02 — Backend platform: **Supabase** (Postgres, Auth, RLS, Storage, Edge Functions). Alternative: Firebase (already used for other Mumtahin apps), but this data is relational and report-heavy and per-read pricing is a risk
- D-04 — Multi-tenancy: One shared database; every tenant row carries `institution_id`; isolation enforced by Postgres RLS, not by app code
- D-05 — Auth in v1: Admin-provisioned accounts; sign in with phone number or username plus password; guardians join by invite link. OTP and self-serve signup come later (they add gateway cost and dependency)

### 5.2 Steps (do them in this order)
After every step: run the fast check (pnpm lint && pnpm typecheck), then commit with the message `M0-P3: step N`.
If a step shows that the task needs something outside its scope, do not work around it: note it under "Requests" or go to section 10.

**Step 1.** Migration creating the core tenancy tables in their final shape per `docs/spec/domain-model.md`: `institutions`, `profiles`, `memberships` with RLS (a user reads only their own profile, their own memberships and the institutions they belong to). M1-P1 extends these; it must not have to rewrite them.

**Step 2.** Skeleton auth with Supabase email and password (the real D-05 flows come in M1-P2), seed script for staging with 2 institutions and 3 users (one user has two memberships). Random passwords, stored by the Owner, never in the repo.

**Step 3.** Web: sign-in page, institution picker (only if the user has more than one), dashboard showing the user's name and institution name, sign-out, session persistence, route guards. Put these pages in `apps/web/src/features/skeleton/**` with a `register.ts` (discovered by the shell from M0-W1); M1-W2 replaces and removes them.

**Step 4.** Deploy: Netlify builds `main` to staging automatically; a GitHub Action applies migrations to staging before the deploy and blocks it on failure.

**Step 5.** Playwright smoke test against the deployed staging URL: sign in, see the institution name. Plus an RLS probe: user A calls the API with A's token and cannot read institution B or its memberships.

**Step 6.** CI check that fails when the built bundle contains the service-role key or the string `service_role`.

**Step 7.** `docs/runbooks/deploy.md`: how deploys work, how to roll back, where each secret lives.

**Context for the steps:** Prerequisites from the Owner (M0-O0): Supabase staging project exists and its secrets are set in GitHub Actions secrets; a Netlify site is connected to the repo. If something is missing, report BLOCKED with the exact checklist. Never ask for secrets in chat.

## 3. Project context (so you are never lost)
- Product: a Bangla-first school management system for schools, madrasas and coaching centres in Bangladesh, built so an institution can run everything on a phone. It is a separate paid product; Munshi is a different, free, single-user app.
- Stack: TypeScript (strict), React 19, Vite, Tailwind, shadcn/Radix, Supabase (Postgres, RLS, Edge Functions), pnpm monorepo, Netlify.
- Layout: `apps/web`, `packages/{domain,db,ui,config}`, `supabase/`, `e2e/`, `docs/`.
- Tenancy: one database; every tenant row has `institution_id`; isolation is enforced by Postgres RLS, never by app code.
- Roles: platform owner, institution admin, teacher, accountant, guardian, student.
- Phone-complete: every task must work on a 360 px phone with touch only (Android first, iPhone second).
- Numbers: money in integer poisha; marks in integer hundredths inside calculations; never floating point.
- Language: Bangla first, English second; all user-visible text goes through i18n keys.
- Quality bar: WCAG 2.2 AA, `docs/spec/ux-standard.md`, and the Definition of Done in README section 9.

**Decisions in force for this task (do not reopen them, except any marked "under review"; for those, do not make the choice yourself: use what the task says and note it in the report):**

### 5.2 Steps (do them in this order)
After every step: run the fast check (pnpm lint && pnpm typecheck), then commit with the message `M1-W4: step N` and push (`git push`), so the Owner and the Leader can see progress and your last-activity time stays fresh.
If a step shows that the task needs something outside its scope, do not work around it: note it under "Requests" or go to section 10.

**Step 1.** `EntryGrid` in `packages/ui` or `apps/web/src/shared` (decide and record in an ADR): rows are students, columns are fields; sticky header and sticky first column; keyboard model: arrows and Tab move, Enter moves down, Escape cancels.

**Step 2.** Phone mode: for one active column, a list of rows (student name and one input per row) with a numeric keypad (`inputmode=decimal`), a Next key that moves down and a progress line (n of N entered); for several columns, a focused-cell editor with next and previous buttons.

**Step 3.** Cell types: number with min and max, code (for example absent), text. Bangla digits are accepted and normalised.

**Step 4.** Inline validation per cell with translated messages; an invalid cell keeps its value.

**Step 5.** Save-state indicator per row (Saved, Saving, Pending n, Error) driven by a callback contract, so M2-E2 can plug in the offline queue from M0-S2.

**Step 6.** Virtualised rows; smooth with 100 rows by 12 columns on a throttled profile.

**Step 7.** Accessibility: grid semantics, labels such as name, subject and marks, focus never hidden by sticky bars.

**Step 8.** Showcase in `/dev/kit` and tests.

**Context for the steps:** Marks entry is subject-wise: one teacher fills one column for a whole class. That is the biggest difference from Munshi's student-by-student entry, and the grid is the core of M2-E2.

## 3. Project context (so you are never lost)

- Product: a Bangla-first school management system for schools, madrasas and coaching centres in Bangladesh, built so an institution can run everything on a phone. It is a separate paid product; Munshi is a different, free, single-user app.
- Stack: TypeScript (strict), React 19, Vite, Tailwind, shadcn/Radix, Supabase (Postgres, RLS, Edge Functions), pnpm monorepo, Netlify.
- Layout: `apps/web`, `packages/{domain,db,ui,config}`, `supabase/`, `e2e/`, `docs/`.
- Tenancy: one database; every tenant row has `institution_id`; isolation is enforced by Postgres RLS, never by app code.
- Roles: platform owner, institution admin, teacher, accountant, guardian, student.
- Phone-complete: every task must work on a 360 px phone with touch only (Android first, iPhone second).
- Numbers: money in integer poisha; marks in integer hundredths inside calculations; never floating point.
- Language: Bangla first, English second; all user-visible text goes through i18n keys.
- Quality bar: WCAG 2.2 AA, `docs/spec/ux-standard.md`, and the Definition of Done in README section 9.

**Decisions in force for this task (do not reopen them, except any marked "under review"; for those, do not make the choice yourself: use what the task says and note it in the report):**

- D-04 — Multi-tenancy: One shared database; every tenant row carries `institution_id`; isolation enforced by Postgres RLS, not by app code

### 5.2 Steps (do them in this order)

After every step: run the fast check (pnpm lint && pnpm typecheck), then commit with the message `M1-A2: step N` and push (`git push`), so the Owner and the Leader can see progress and your last-activity time stays fresh.
If a step shows that the task needs something outside its scope, do not work around it: note it under "Requests" or go to section 10.

**Step 1.** Migrations for `students`, `guardians`, `student_guardians`, `enrollments`, `enrollment_subjects` with constraints, RLS, audit triggers and tests (including guardian-own-children and teacher-assigned-sections cases).

**Step 2.** UI: list with search (Bangla and English names, roll, code), filters (class, section, status), create and edit student with guardians, structured address using a static Bangladesh division to upazila dataset (record its source and licence in `docs/decisions/0007-address-data.md`), optional photo (compressed to about 300 KB or less), enrolment with roll numbers (auto-assign by name order as an option), status changes with reasons (left, transferred, graduated), archive and restore.

**Step 3.** Replace the `students`, `guardians` and `student_guardians` stand-ins in `supabase/tests/plat/020_helpers.test.sql` with the real tables, exactly as `M1-A1` did for `teacher_assignments` (Leader ruling R-16): change only what the real tables replace, never weaken or delete an assertion, adjust `plan(N)`.

**Step 4.** Add a nullable `profile_id` to `students` (unique per institution when set; not used by any v1 screen) so the `private.is_student_self` helper can work later (Leader ruling R-14; `docs/spec/domain-model.md` section 4).

**Step 5.** Duplicate warning (same name and date of birth, or same name and guardian phone) that does not block saving.

**Step 6.** Quick add for phones: add a student in 30 seconds or less, with class and section remembered between entries (save and add next).

**Step 7.** Phone fields use `normalizeBdPhone` from `@sms/domain`.

**Context for the steps:** Students are minors; collect only what the spec lists. Guardian access to own children is enforced now in RLS even though the guardian UI arrives in M3.

## 3. Project context (so you are never lost)
- Product: a Bangla-first school management system for schools, madrasas and coaching centres in Bangladesh, built so an institution can run everything on a phone. It is a separate paid product; Munshi is a different, free, single-user app.
- Stack: TypeScript (strict), React 19, Vite, Tailwind, shadcn/Radix, Supabase (Postgres, RLS, Edge Functions), pnpm monorepo, Netlify.
- Layout: `apps/web`, `packages/{domain,db,ui,config}`, `supabase/`, `e2e/`, `docs/`.
- Tenancy: one database; every tenant row has `institution_id`; isolation is enforced by Postgres RLS, never by app code.
- Roles: platform owner, institution admin, teacher, accountant, guardian, student.
- Phone-complete: every task must work on a 360 px phone with touch only (Android first, iPhone second).
- Numbers: money in integer poisha; marks in integer hundredths inside calculations; never floating point.
- Language: Bangla first, English second; all user-visible text goes through i18n keys.
- Quality bar: WCAG 2.2 AA, `docs/spec/ux-standard.md`, and the Definition of Done in README section 9.

**Decisions in force for this task (do not reopen them):**
- D-14 — UX standard and process: ISO 9241-210 process (interviews, flows, prototypes, user tests, pilot evaluation); WCAG 2.2 AA; Nielsen heuristics as review checklist; Core Web Vitals targets; `docs/spec/ux-standard.md` is binding

### 5.2 Steps (do them in this order)

**Step 1.** `prototypes/`: static HTML, CSS and JS (no build step; opens from a phone) using the design tokens. Flows: (1) teacher takes daily attendance on a phone, with offline and sync states; (2) teacher enters marks for one subject for a whole class in the grid, with validation, an absent code and save state; (3) admin reviews results, publishes and previews a marksheet; (4) admin adds students on a phone: quick add, paste a list, or pick a file (mapping, errors, commit); (5) guardian sees a child's attendance, a published result and notices.

**Step 2.** Realistic Bangla sample data (names, subjects, marks). No real student data anywhere.

**Step 3.** Failure paths that matter: wrong mark, missing header, locked exam, no connection.

**Step 4.** Test on real phones (a low-end Android; an iPhone if possible), including states with the on-screen keyboard open; turn the hassle targets in `docs/spec/mobile-complete.md` §5 into task success criteria.

**Step 5.** `docs/research/usability-test-plan.md` in Bangla: participants (5 to 8 across roles), tasks with success criteria and target times, think-aloud script, consent script, scoring sheet (success, time, errors, satisfaction 1 to 5, comments).

**Step 6.** `docs/research/usability-findings-template.md`.

**Context for the steps:** ISO 9241-210 asks for user-tested design solutions before build (see `docs/research/ux-standards.md`). The Owner runs the sessions (M1-O4) without the agent.

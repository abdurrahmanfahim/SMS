## 3. Project context (so you are never lost)
- Product: a Bangla-first school management system for schools, madrasas and coaching centres in Bangladesh, built so an institution can run everything on a phone. It is a separate paid product; Munshi is a different, free, single-user app.
- Stack: TypeScript (strict), React 19, Vite, Tailwind, shadcn/Radix, Supabase (Postgres, RLS, Edge Functions), pnpm monorepo, Netlify.
- Layout: `apps/web`, `packages/{domain,db,ui,config}`, `supabase/`, `e2e/`, `docs/`.
- Tenancy: one database; every tenant row has `institution_id`; isolation is enforced by Postgres RLS, never by app code.
- Roles: platform owner, institution admin, teacher, accountant, guardian, student.
- Phone-complete: every task must work on a 360 px phone with touch only (Android first, iPhone second).
- Numbers: money in integer poisha; marks in integer hundredths inside calculations; never floating point.
- Language: Bangla first, English second; all user-visible text goes through i18n keys.
- Quality bar: WCAG 2.2 AA, `docs/spec/ux-standard.md`, and the Definition of Done in README section 9.

**Decisions in force for this task (do not reopen them, except any marked "under review"; for those, do not make the choice yourself: use what the task says and note it in the report):**

### 5.2 Steps (do them in this order)
After every step: run the fast check (pnpm lint && pnpm typecheck), then commit with the message `M1-Q1: step N` and push (`git push`), so the Owner and the Leader can see progress and your last-activity time stays fresh.
If a step shows that the task needs something outside its scope, do not work around it: note it under "Requests" or go to section 10.

**Step 1.** Playwright projects for local and staging; seed with 2 institutions and users for each role (through a script that uses the service role locally only).

**Step 2.** `loginAs(role, institution)` helper and page objects for sign-in and navigation.

**Step 3.** `supabase/tests/rls-registry.json`: lists every table in `public` with the roles expected to read and write; a CI check fails if a table is missing from it or if no test references it.

**Step 4.** API probe suite: for each registered table, with each role's JWT, attempt select, insert, update and delete against the REST API on own tenant and the other tenant; compare with the registry expectations.

**Step 5.** Smoke flows: sign in, create student, import CSV, sign out.

**Step 6.** Accessibility gate: axe-core runs in Playwright on the main screens and fails CI on serious or critical violations.

**Step 7.** Phone projects: Playwright device emulation for a low-end Android profile (360x640, CPU and network throttled) and an iPhone; the smoke flows and the axe gate run in the phone projects, not only on desktop.

**Step 8.** CI: separate jobs `rls` and `e2e`; failure output names the table and role.

**Context for the steps:** `M1-P1` provides `supabase/tests/helpers.sql`. This task adds the API-level probe and the registry that forces every new table to be covered.

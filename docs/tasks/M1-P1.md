## 3. Project context (so you are never lost)
- Product: a Bangla-first school management system for schools, madrasas and coaching centres in Bangladesh, built so an institution can run everything on a phone. It is a separate paid product; Munshi is a different, free, single-user app.
- Stack: TypeScript (strict), React 19, Vite, Tailwind, shadcn/Radix, Supabase (Postgres, RLS, Edge Functions), pnpm monorepo, Netlify.
- Layout: `apps/web`, `packages/{domain,db,ui,config}`, `supabase/`, `e2e/`, `docs/`.
- Tenancy: one database; every tenant row has `institution_id`; isolation is enforced by Postgres RLS, never by app code.
- Roles: platform owner, institution admin, teacher, accountant, guardian, student.
- Phone-complete: every task must work on a 360 px phone with touch only (Android first, iPhone second).
- Numbers: money in integer poisha; marks in integer hundredths inside calculations; never floating point.
- Language: Bangla first, English second; all user-visible text goes through i18n keys.
- Quality bar: WCAG 2.2 AA, `docs/spec/ux-standard.md`, and the Definition of Done in README section 9.

**Decisions in force for this task (do not reopen them, except any marked "under review"; for those, do not make the choice yourself: use what the task says and note it in the report):**
- D-04 — Multi-tenancy: One shared database; every tenant row carries `institution_id`; isolation enforced by Postgres RLS, not by app code

### 5.2 Steps (do them in this order)

**Step 1.** `institution_settings`, `platform_admins` and `audit_log` (append-only, enforced by privileges and a trigger) per the spec.

**Step 2.** All `private` helper functions in `docs/spec/permissions.md` §3 with the exact signatures; teacher and guardian helpers may reference tables that arrive later, so create them in a way that works once those tables exist (guard with a follow-up migration owned by ACAD if needed, and record it).

**Step 5.** Trigger that makes `institution_id` immutable, exposed as a reusable function.

**Step 6.** `supabase/tests/helpers.sql`: creates two institutions with one user per role and helper functions to act as a user in pgTAP tests.

**Step 7.** pgTAP tests for every table and policy in this task: allowed role passes, other role fails, other tenant fails.

**Step 8.** `docs/spec/rls-patterns.md`: how to add a table safely (checklist and copyable examples).

**Step 9.** Storage: private buckets `logos`, `photos`, `imports` and `exports`, with policies that allow access only under the path `<institution_id>/...` for members of that institution (by role), short-lived signed URLs, size limits per bucket, and tests that another tenant cannot list, read or write.

**Context for the steps:** M0-P3 already created `institutions`, `profiles` and `memberships` in their final shape with basic policies. Extend them; do not rewrite them and do not break the staging skeleton.

### 5.5 Common mistakes for this kind of work
- Every table needs RLS enabled, policies, and tests for: allowed role passes, other role fails, other tenant fails.
- Use composite tenant foreign keys `(institution_id, parent_id)`; never trust `institution_id` sent by a client.
- Migrations are forward-only and named `YYYYMMDDHHMM_plat_<desc>.sql`; never edit an applied one. Regenerate and commit `packages/db/src/types.ts`.
- `SECURITY DEFINER` functions must set `search_path` to empty and check the caller's role and tenant inside.
- The service-role key exists only in server code and CI secrets. Never in the client bundle, logs or docs.

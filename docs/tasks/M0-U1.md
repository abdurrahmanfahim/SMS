## 3. Project context (so you are never lost)
- Product: a Bangla-first school management system for schools, madrasas and coaching centres in Bangladesh, built so an institution can run everything on a phone. It is a separate paid product; Munshi is a different, free, single-user app.
- Stack: TypeScript (strict), React 19, Vite, Tailwind, shadcn/Radix, Supabase (Postgres, RLS, Edge Functions), pnpm monorepo, Netlify.
- Layout: `apps/web`, `packages/{domain,db,ui,config}`, `supabase/`, `e2e/`, `docs/`.
- Tenancy: one database; every tenant row has `institution_id`; isolation is enforced by Postgres RLS, never by app code.
- Roles: platform owner, institution admin, teacher, accountant, guardian, student.
- Phone-complete: every task must work on a 360 px phone with touch only (Android first, iPhone second).
- Numbers: money in integer poisha; marks in integer hundredths inside calculations; never floating point.
- Language: Bangla first, English second; all user-visible text goes through i18n keys.
- Quality bar: WCAG 2.2 AA, `docs/spec/ux-standard.md`, and the Definition of Done in README section 9.

**Decisions in force for this task (do not reopen them, except any marked "under review"; for those, do not make the choice yourself: use what the task says and note it in the report):**
- D-14 — UX standard and process: ISO 9241-210 process (interviews, flows, prototypes, user tests, pilot evaluation); WCAG 2.2 AA; Nielsen heuristics as review checklist; Core Web Vitals targets; `docs/spec/ux-standard.md` is binding
- D-15 — Flow relative to Munshi: Different flow (role- and task-based, subject-wise marks grid, exam wizard), same design language and interaction rules; see `docs/research/munshi-flow-analysis.md`
- D-16 — Mobile-complete: Every task in every role can be done on a phone alone, comfortably, with no laptop. Android first, iPhone second; tablets and desktops are enhancements. `docs/spec/mobile-complete.md` is binding; acceptance is a phone-only run of the whole journey (`M2-Q3`)

### 5.2 Steps (do them in this order)
After every step: run the fast check (re-read what you produced against the step), then commit with the message `M0-U1: step N` and push (`git push`), so the Owner and the Leader can see progress and your last-activity time stays fresh.
If a step shows that the task needs something outside its scope, do not work around it: note it under "Requests" or go to section 10.

**Step 1.** `docs/spec/ux-flows.md`: for each role a home definition (what appears first and why), the top 5 tasks with tap counts from home (project rule: primary tasks within 2 taps), and one Mermaid flow per task.

**Step 2.** Navigation map: mobile bottom tab bar (at most 5 items) and desktop sidebar per role, using the `NavItem` contract from M0-W1; labels in Bangla with English alternatives.

**Step 3.** Screen inventory table: ID (S-001 and up), name, role or roles, route, purpose, data shown, primary action, states (loading, empty, error, locked, offline) and the task that builds it (for example M1-A1).

**Step 4.** New-institution setup journey from first sign-in to first published result, as a checklist-driven onboarding that says which steps can be skipped or done later.

**Step 5.** Keep, change and drop table for Munshi interactions, with reasons (start from the analysis).

**Step 6.** Phone-only journey per role: for every top task describe the phone flow, using the task matrix in `docs/spec/mobile-complete.md`; flag any task that has no comfortable phone flow yet (import, bulk print, wide reports, complex editors) and propose a pattern.

**Step 7.** Open questions for the Owner and for the interviews.

**Context for the steps:** SMS is role- and task-based; Munshi is a one-person drill-down through Year, Class and Form (see the analysis). Roles: institution admin, teacher, accountant, guardian, platform owner. Scope is M1 and M2; M3 features (fees, alerts, parent portal) appear as placeholders. Interview findings (M0-O1) and the competitor teardown (M0-R1) refine this when they arrive; start from the Munshi analysis.

# PDF spike — Bangla marksheet PDF and print (M0-S1)

## Environment note (read first)
The execution environment for this spike (a sandboxed container) could not reach headless
Chromium: Playwright's browser-download CDN (`playwright.azureedge.net` and mirrors) is not on
the network allowlist, and Ubuntu 24's `chromium-browser` package is a transitional shim to a
snap, which is unavailable (no snapd). This means **Approach A and B could not be executed or
benchmarked with the literal Chromium/Playwright stack named in the task.**

To still get real, run evidence rather than guesses, this spike substitutes **wkhtmltopdf**
(Qt WebKit print-to-PDF, already present in the environment) for the "browser print engine"
half of Approaches A and B. wkhtmltopdf is older and no longer actively developed, and its
numbers are **not a stand-in for Chromium's** — Chromium is expected to be faster, more
memory-hungry, and more standards-compliant (modern `@page`/CSS Grid support, better font
fallback tables). Where this doc gives a wkhtmltopdf number, it is labelled as such. Section
"What M2-E4 still needs to verify" lists what a real Chromium/Playwright run must re-check.

## Layouts tested
Built in `spikes/pdf/layouts/`, generated by `spikes/pdf/layouts/generate.mjs` (no dependencies):
1. **Layout 1** — 8–12 subjects, per-subject grade + GPA, total, merit position.
2. **Layout 2** — subjects with components (written / MCQ / practical) + class-test column.
3. **Layout 3** — transcript style, header + signature blocks.

A 100-student batch (`layout1-batch100.html`, 12 subjects) was generated for the batch test.

## Bangla stress-test set
Embedded as student names across all three layouts (`generate.mjs`, `stressNames`):
conjuncts ক্ষ, ন্ত, শ্র, reph (র্), ya-phala (্য); Bangla digits; Bangla+English mixed;
Bangla+Arabic mixed; one very long name (44 chars).

## Approach A — print CSS → PDF (browser engine)
**Tested with wkhtmltopdf** (Chromium not runnable here — see environment note).

| Layout | Result |
|---|---|
| Layout 1, single sheet | Correct A4 layout, table borders, header/footer, signatures. `docs/research/pdf-spike/approach-a-layout1-1.png` |
| Layout 2 | Correct, including the ক্ষ conjunct in "ক্ষিতীশ". `approach-a-layout2-1.png` |
| Layout 1, 100-student batch | All 100 sheets paginate correctly via `page-break-after`; Arabic-mixed name (page 7) renders with correct RTL Arabic shaping via automatic system-font fallback — the WebKit engine substitutes a font for the codepoints it doesn't have in Noto Sans Bengali, something Approach C's single-font pipeline could not do. `approach-a-batch-p-007.png`. The 44-char long name (page 8) wraps within its cell with no overflow. `approach-a-batch-p-008.png` |

**Batch timing/memory (wkhtmltopdf, this container, 100 sheets, `/usr/bin/time -v`):**
wall time **7.71s**, peak RSS **89 MB** (91172 KB), 99% CPU (single-threaded render).
Output file: **32.5 MB** (317.6 KB/page average) — wkhtmltopdf does not appear to de-duplicate
the embedded Bangla font across pages, so file size scales roughly linearly with page count.
This is a real cost to check with Chromium: if Chromium's PDF writer shares the font object
across pages (typical for a well-formed multi-page PDF), the batch file should be far smaller —
this needs re-verification once Chromium is reachable.

Evidence: `docs/research/pdf-spike/approach-a-wkhtmltopdf-layout1.pdf`,
screenshots above, and the report's Verify output section.

## Approach B — headless Chromium as a server (Playwright)
**Could not run** — Playwright's Chromium download is blocked by this container's network
allowlist (confirmed: 403 "Host not in allowlist" from `playwright.azureedge.net`,
`playwright-akamai.azureedge.net`, `playwright-verizon.azureedge.net`). The code path is
identical to Approach A's HTML/CSS (same layouts), so once a machine with a real Chromium is
available, the only new work is a thin Playwright wrapper (`page.pdf()`) and re-running the
same batch/timing/memory measurement. No timing, memory, or cost numbers can be reported —
marking that criterion unticked rather than estimating.

**Where it could run:** not Supabase Edge Functions (no headless-browser support there); a
small container service (e.g. a Cloud Run / Fly.io / a small VPS container running
`node:20-slim` + Chromium) is the conventional fit, invoked from an Edge Function or the app
server over HTTP.

## Approach C — client-side PDF library + embedded Bangla font
Tested with `pdfkit` 0.15 + `fontkit` (its font engine) + the Noto Sans Bengali TTF, in
`spikes/pdf/approach-c/render.mjs`. Result: `docs/research/pdf-spike/approach-c-render-1.png`.

- fontkit does some GSUB substitution, so several conjuncts (ক্ষ, ন্ত, শ্র) render legibly —
  better than a naive "no shaping at all" library would.
- **The mixed Bangla+Arabic name renders as tofu boxes (□).** pdfkit/fontkit only draws glyphs
  from the one font you hand it; there is no per-run font-fallback the way a browser engine has.
  A production client-side pipeline would need to pre-segment text by script and swap fonts
  per run itself — extra complexity a browser print engine gets for free.
- This was a "quick check" per the task's own framing (step 4); it was not benchmarked for
  timing/memory/batch, since Approach A/B already look viable and cover the batch case better.

## Licence of every embedded font
Noto Sans Bengali — **SIL Open Font Licence 1.1 (OFL-1.1)**, from the `notofonts/bengali`
project (built binary pulled from `google/fonts`, `ofl/notosansbengali/`). OFL-1.1 explicitly
permits embedding in documents and redistribution; no attribution file is required at runtime,
only within the font's own package if redistributed as a font. No other font was embedded.

## Recommendation
**Print CSS through a real browser engine (Approach A/B family) is the right direction for
D-12**, with Approach C (client-side lib) as a fallback only for a simple single-subject-list
layout where no script mixing is expected (Bangla + Bangla digits only, no Arabic/English
names) — even then, conjunct shaping was inconsistent enough in this test that I would not
default to it.

Specifically:
- **Primary:** Approach B (headless Chromium behind a small container service), because it
  covers the 100-student batch case, multi-script fallback (the Arabic-name case is realistic
  — Bangladeshi student/guardian names do include Arabic-script segments), and gives a PDF a
  guardian can view/share/print from a phone via a normal download.
- **Fallback:** if the container service is briefly down, on-device Approach A (print CSS,
  the phone's own browser "Print to PDF") for a single marksheet — this needs no server round
  trip and phone browsers already have Bangla-capable rendering (this needs on-device
  confirmation per the phone-evaluation gap above).
- **Do not** default to Approach C for anything with mixed-script names unless a proper
  per-run font-fallback layer is added first.

**This spike's confidence in the recommendation is real but incomplete**: it rests on
wkhtmltopdf standing in for Chromium. The shaping/fallback behaviour is very likely to transfer
(both are browser-class engines with real text-shaping stacks, unlike Approach C), but the
timing, memory, file-size and phone-usability numbers are not yet confirmed with the actual
target engine and are the concrete next steps.

## Outline for M2-E4 (template model, font embedding, batch strategy, file naming)
- **Template model:** one HTML+CSS template per marksheet type (mirrors `spikes/pdf/layouts/`
  1–3), data-driven from a typed marksheet view model in `@sms/domain`; no per-institution
  template forking — customise via a small set of documented slots (logo, signature labels).
- **Font embedding:** ship Noto Sans Bengali (OFL-1.1) as the default; verify Chromium
  de-duplicates the embedded font object across a batch PDF (item 2 above) before committing to
  batch generation at scale.
- **Batch strategy:** one Chromium `page.pdf()` call per student is simplest but was not timed
  here; an alternative is one long HTML document with `page-break-after` per student (as this
  spike's `layout1-batch100.html` does) rendered in a single `page.pdf()` call — this spike's
  wkhtmltopdf numbers suggest the single-document approach is viable time-wise (7.7s/100
  sheets) but the file-size problem needs to be solved first (see item 2).
- **File naming:** suggest `<institution_id>/<exam_id>/<student_id>.pdf`, stable and
  re-generatable, so a re-render overwrites rather than duplicates.
